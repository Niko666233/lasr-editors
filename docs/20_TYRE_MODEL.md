# 20 · 轮胎模型（Pacejka）全解

> P5 第四块，也是「手感」里最实的一块。**结论：轮胎不是黑箱 —— 它就是
> 11 个配方 × 6 种路面 × 36 个系数槽，数据全在 Java 侧，语义由原生 setter 与
> 系数索引表白纸黑字给定。**
> 工具：`tools/tyre_dump.py` → `out_tyres.json`

## 1. 从原生侧来的三条硬约束（先有语义，再谈数值）

`WheelRef.setPacejka` 有三个重载（`(IF)V`、`(IIF)V`、`(I[I[F)V` @0x483400/0x483460/0x4834e0）。
数组版反汇编：

```asm
cmp  eax, 0x20
jge  <错误退出>                        ; ★ arg1（轮胎槽位）必须在 [0, 32)
...
cmp  esi, ebp                          ; idxs.length vs vars.length
jge  ...
push 0x6edfd4 ; call 0x5668d0          ; ★ 'inconsistent Pacejka array sizes! (%d,%d)'
...
循环 i:
  varIdx = <int[] 取第 i 项>            ; 辅助函数 0x6438b0
  val    = <float[] 取第 i 项>          ; 辅助函数 0x6438d0
  if (varIdx == 0x12) val *= 1e-4      ; ★ 第 18 号槽有单位换算
  lea ecx, [eax + eax*8]               ; ★ ×9
  lea edx, [edi + ecx*4]
  movss [ebx + edx*4 + 0x20c], val     ; ★ 目标 = tyreObj + 0x20c + varIdx*4 + arg1*144
```

⇒ 三条硬约束：

1. **系数数组基址 = `tyre + 0x20c`**，每颗轮胎 **144 字节（36 个 f32 槽）**；
2. **索引的作用域是 0..35**（`pacVarIdxs_v3` 里出现了 34/35 ⇒ 槽位不止 32）；
3. **槽 18（0x12）写入时要乘 `1e-4`** —— 一个真实存在的单位换算，重制时若漏掉，
   那一条系数会差 4 个数量级。

## 2. 系数索引表（Java `PacejkaGlobals`，已从伪码读出）

```java
CONTACT_Asphalt=0 Grass=1 Gravel=2 Hard_Sand=3 Snow=4 Ice=5 Count=6   // ★ 6 种路面

pacVarIdxs    = {2,12,0,4,13,11,14,3,17,10,1,6,7,8,18,19}              // 16 系数版
pacVarIdxs_v2 = {2,12,0,4,13,11,14,3,17,10,1,6,7,8,18,19,15,16}        // 18 系数版
pacVarIdxs_v3 = {2,12,0,4,13,11,14,3,17,10,1,6,7,8,18,19,15,16,34,35}  // 20 系数版

common_pacVarIdxs = {15,16,26,24,25,22,23}
common_pacVars    = {1000.0, 6000.0, 10.0, 0.0, 0.0, 1.0, 1.0}
```

⇒ 每个配方给的是**稠密的一行**，位置经 `pacVarIdxs*` 映射到 36 槽数组的对应槽位。
v1/v2/v3 不是版本号而是**三套不同的系数集合**（16/18/20 个）。

`common_pacVars` 是全局共用项：`{1000, 6000, 10, 0, 0, 1, 1}` 填在
槽 `{15,16,26,24,25,22,23}` —— 看数值像「参考载荷/最大载荷/温度/…」一组标准量
（1000/6000 很像 kg 与 N 的成对量，10.0 像某个上限），**具体语义待逐个确认**
（★ 部分已在 `docs/37_PACEJKA_SLOTS.md` 标定：槽 0/2/4/11/12/14 已命名，
0/4/11/12/14 由 C++ setter 的写入偏移给出，槽 2 由数据差值独立给出）。

## 3. 11 个配方（`out_tyres.json`，全部导出）

每个配方的 6 行路面表里，**除了第一项（µ）以外通常完全相同**，所以下表列 µ：

| 配方 | 索引集 | 系数数 | 沥青 µ | 草地/碎石/硬沙 µ | 雪 µ | 冰 µ |
|---|---|---|---|---|---|---|
| `Tyre_RH` | v2 | 18 | 2.00 | 2.00 | 2.00 | 0.10 |
| `Tyre_RM` | v2 | 18 | 2.17 | 2.17 | 2.17 | 0.17 |
| `Tyre_RS` | v2 | 18 | 2.25 | 2.25 | 2.25 | 0.25 |
| `Tyre_SH` | v3 | 20 | 1.50 | 1.50 | 1.50 | 0.30 |
| `Tyre_SH_B` | v3 | 20 | 1.50 | 1.50 | 1.50 | 0.30 |
| `Tyre_SM` | v2 | 18 | 1.66 | 1.66 | 1.66 | 0.16 |
| `Tyre_SS` | v2 | 18 | 1.85 | 1.85 | 1.85 | 0.25 |
| `Tyre_NC` / `Tyre_NC_B` | v3 | 20 | 1.30 | 1.30 | 1.30 | 0.30 |
| `Tyre_XD` | v2 | 18 | 1.20 | 1.40 | 1.20 | 0.20 |
| `Tyre_XD_B` | v2 | 18 | 1.40 | 1.60 | 1.30 | 0.30 |

**★ 独立判据（槽位映射正确性）**：配方名的软硬顺序必须与 µ 单调一致 ——
`RH(硬) 2.00 < RM 2.17 < RS(软) 2.25` ✓、`SH(硬) 1.50 < SM 1.66 < SS(软) 1.85` ✓。
**如果索引表映射错了，这一列会是噪声；它是完美单调的**，所以位置→槽位的对应是对的。

`Tyre_XD*` 是唯一「按路面区分」的配方（沥青/草地/碎石/硬沙/雪 各不相同）——
说明这套属性本来就能表达全地形差异，只是多数配方没用。

## 7. 轮对象几何（顺手确认的三层结构）

从 `Chassis.getWheelPac(II)F` @0x485250（其真正实现 `0x44c730` 是一个**带步长的索引
存取器**：`if (idx<0 || idx>=c->count) return 0; return c->base + idx*0x334;`）反推出：

| 层 | 偏移 / 步长 | 说明 |
|---|---|---|
| 车 → 轮数组 | `car + 0x20a4` | WheelRef 数组基址 |
| WheelRef 对象 | 步长 **0x1528（5416 B）** | 每颗轮胎一个 |
| WheelRef.Pacejka 系数 | `+0x20c`，36 槽 | 见 §1（`0x20c + 36*4 = 0x29c < 0x1528` ✓ 自洽） |
| WheelRef → 物理记录 | `{u32 count; void* base;}`，元素 **0x334（820 B）** | `getWheelPac` 用 |

另外 `Chassis.getWheelCamber(I)F` 里出现的浮点常量是 **`-1.5707964 = -π/2`** ——
说明它做的是「把某个姿态角折算到 [-π/2, π/2]」的换算，重制时这类角**必须以弧度
（而不是度）实现**。

`getWheelSlip(I)F`（42 条指令、无常量）是纯字段读取 ⇒ 侧滑量在原生里是**直接存的
状态量**，不是每次现算 —— 这也是重制时该保留的设计（每步更新一次状态）。

## 8. 重制时的落地清单

1. `coefficient[36]` 每颗轮胎一份，索引语义照抄 `pacVarIdxs*` 三套；
2. 载入配方时按 6 种路面各存一行（本作多数配方 6 行相同，但结构要留）；
3. **槽 18 的 `1e-4` 缩放不要漏**；
4. 摩擦 µ = 槽 2（`pacVarIdxs` 首位）；冰面 ≈ 沥青的 1/10；
5. 弹簧刚度用「胎壁对照表」而非单一常数；
6. 逐车差异来自 `Tyre_*` 配方引用 + `pacejkaCustomizationInfo = {1,1,1,1}` 四个乘子，
   而**不是**每辆车写死一套系数。
