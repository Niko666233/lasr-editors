规则来源（都在本轮实测里反复对过）
----------------------------------
1) `X = new <类型>[N];`：N 是字面量，字节码顺序 `INT N; NEWARRAY`；
   例 Coupe_RS_IEngine_stock.eRPMs off=1 INT 13 → 0x22。
2) `localK = {v0,v1,...};`：字节码先把值压栈、再压长度（`FLOAT 38.0,4.5,0.85,0.0;
   INT 4; 0x22; 0x24`），所以长度标签排在值后面；宿主字段来自紧跟的 `X.f = localK;`。
   长度值 = 元素个数（字符串元素也算），例如 Hatch_S2_IRims_stock.Rims() 的 8 个字符串
   → 字节码 FLOAT/INT 8，与 `数组长度` 对齐。
3) `X.f[i] = v`：目标数组是 this 的字段或本方法新建的数组时，最内层下标被编进
   0x1C 指令 payload，只有链上第一笔（或「浮点值且上一笔不是整数值」）会显式压下标；
   目标是别的对象的字段（local0.turboTable[i]）时每笔都压下标：
     initPowerCharacter  turboTable 32 笔 = 32 下标 + 32 值（全浮点）
     IRunningGear_stock.<init> EBDParams_F 3 笔 = 1 下标 + 3 值（整数,整数,浮点）
     Coupe_SD_T5_IMuffler_stage_I.RPMs 3 笔 = 3 下标 + 3 值（全浮点）
     Coupe_RS_IEngine_stock.eRPMs 13 笔 = 1 下标 + 13 值（全整数）
   开关实测：--set index_model=first_only 对齐数 3308→3203（更差）。
4) 多维 `X.f[i][j] = v`：外层下标 i 每笔都压，内层 j 只在链上第一笔压：
     Model_Coupe_RS.<init> axleLoadDegradationAtBodyStage 10 笔 = 10 外下标 + 1 内下标
     + 10 值 = 21，与实测一致。开关实测：--set outer_index_always=false 3308→3288。
5) `case N:` 的 N 是字面量（switch 编译成「压 case 值 + 比较」）：算进去 3308，
   不算 3288；所以默认算，标签给 `case值`。
6) 反编译器把 `x = f(n); if ((f(n) != null))` 里的调用重复打印了一遍，
   上一行刚把同一表达式赋给局部量时，if 行里的数字不再算字面量（救回 20 个方法）。

丢弃方法的原因分类（逐类都给过样例）
-----------------------------------
  a) 构造器 super(...) 实参被反编译器吞掉：例如 Hatch_S2_IEngine_stage_I.<init>
     字节码 `INT 1 → IEngine.<init>(I)`，伪码只剩 `initStock(local0);`，个数必然不等。
     该类别 = 失败的大头；本轮已由「规则 C」补上并通过值级校验，见上面那一节。
  a2) 缺口 +1/+3 但过不了规则 C 闸门（没有独立预测值 / 预测值与字节码不符）：
     例如 Hatch_S2_ISteeringWheel_stock 类名说 stock=0，字节码第 1 个实参是 FLOAT 350.0；
     Coupe_SD_T5_ISideskirts_stock 同理（1 != 0）。这类继续留空，不硬补。
  b) 整个方法体被吞：Hatch_S2_INitrous_stage_I.<init> 伪码只有 `return;`，
     字节码还有 3 个字面量（super 的 stage 号 + 1.0 + 0.5）。
  c) 反编译失败：Coupe_SD_T5_Rim_ST.static_getBoneAssigns 头部带
     `[stack analysis failed: unreachable]`，正文只写 `return null;`，
     真正代码只在 `// ---- N block(s) not reached` 注释里（该注释不是伪码行，未解析）。
  d) 伪码乱码：IVehicle_Coupe_RS.<init> 的数组字面量里混进 `None.xxx [I` 这种
     不成对类型描述符，值级校验也会抓到错位（这类方法本来就对不齐，被丢弃）。
  e) 乘数编在指令 payload 里：Sedan_MX_IRunningGear_stage_IV.<init> 的
     `this.DTbrak_F = (((F)1900) * 1.25);` 只有 1900 是字面量，
     1.25 在 0x1C 的 payload（pay=2684354566=0xA0000006，高位就是 1.25 的 float 高位）里。

不确定处（逐条）
----------------
  1. "<被调用者>#参数N"（占标签大头）只表示「这一行的第 N 个实参」，不是引擎字段名；
     实参位置的判定基于伪码的调用括号，值级校验只能保证顺序/取值一致，
     不能保证语义（同一位置多个 0.0 时看不出来）。
  2. "<字段>#下标" 表示「写这个元素时编译器显式压了的下标字面量」，
     下标何时显式压是按实测模型推的（见规则 3/4），个别类可能有偏差——
     但凡偏差都会让个数不等而被丢掉，不会静默错位。
  3. 少数类的伪码与字节码不同步：Hatch_Trend_IEngine_stock 的 eRPMs/eMuls
     伪码值是字节码的一半（954 vs 1908…），值级校验能抓到；这两条方法仍在 JSON 里
     （个数相等、标签描述的是「数组第 i 项」这一位置语义），但它的数值不可信。
  4. 二维 `int[][]` 数组字面量的长度占位在字节码里是 -1（真长度在 0x24 payload），
     这类位置的值级校验按例外放行（IVehicle_Hatch_S2.<init> 的 stylingIDs）。
  5. 伪码打印只有约 7 位有效数字（4.28 对应字节码 4.279999732971191），
     值级校验用 1e-6 相对容差，所以「相邻两个字面量数值很接近」的错位抓不出来（少见）。
  6. 只覆盖 vehicles/<Car>/<body>/classes.zip 下的 1850 个类；
     out_pseudo 里另外 34 个（vehicles/classes 等）不在本次范围。
  7. 「规则 C」补出来的 `<父类>.<init>#参数N`：第 1 个实参的数值由**类名层级记号**
     预测（与字节码独立），第 2..k 个由**别的车体**在同一父类构造器约定里压过的
     常量预测（leave-one-group-out）。因此：单个类或单个车体偏离一定会被逐条比对
     抓住；但若**所有车体**在同一个约定上都用错值（例如 INitrous 的 1.0/0.5 若有
     系统性偏差），本闸门看不出来 —— 这两条是那份 50 条 +3 的唯一薄弱点，已明示。
     结构层（前导字面量个数 / 位置 / owner / 形参类型）是逐条从字节码证明的，不依赖预测。
